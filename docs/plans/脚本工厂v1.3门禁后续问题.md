# 脚本工厂v1.3门禁后续问题

状态：已记录，暂不纳入本次五项门禁修复。

## 1. 复审覆盖审计历史

当前复审可能覆盖原审计结果和人工处理轨迹。后续应设计追加式审计版本，保留每次审计、人工处理及版本间关系，不能用新结果静默替换旧记录。

结论：需要独立修复。它涉及审计记录模型和历史读取方式，不应混入本次门禁关键路径修复。

## 2. 同一IP的待审稿互相覆盖

当前待审区主要按IP定位记录，同一IP并行产生多份待审稿时存在静默覆盖风险。后续应引入独立草稿标识和列表语义，确保每份待审稿可单独恢复、审计和提升。

结论：需要独立修复。它涉及待审存储结构迁移，范围明显超过本次五项问题。

## 3. 人工放行绕过统一正式写入流程

人工放行后的正式写入目前可能没有完整复用正常生成流程，导致选题关联、知识使用记录等业务信息缺失。后续应抽取统一的正式写入入口，让自动通过和人工放行共享同一套写入及关联逻辑。

结论：需要独立修复。当前门禁安全性可以先闭合，但在统一写入完成前，不能宣称人工放行后的业务数据链路已经完整。

## 4. 页面关闭后迟到响应仍可能写入

当前生成、审计或人工确认请求发出后，如果用户关闭页面，迟到的响应仍可能继续更新待审存储，甚至触发正式写入。后续应增加页面生命周期失效标记，并在每次持久化前再次核对请求仍属于有效页面任务。

结论：作为独立P2处理。本轮只修复“人工补充案例尚未核实却未进入服务端待办与门禁”的P1，不扩大到页面卸载时序。

## 拆分理由

本次五项修复直接处理错误放行、故障后继续入库、迟到确认和正式稿提前覆盖。以上四项分别涉及审计历史模型、待审存储模型、业务关联写入和页面卸载时序，合并处理会扩大数据迁移与审查范围，因此单独排期更安全。
