# 人工复盘与知识学习能力实施路线图

状态：方案已确认，暂未开始实施。本文档同时承载人工复盘、知识效果追踪、全库查重与入库价值判断的统一路线图。

## 一、路线图结论

可以并行推进，互不依赖：

1. 知识效果追踪：打通“知识条目→脚本→发布复盘→真实表现”的关联，修正“已用于脚本”记录时机过早的问题。
2. 人工复盘功能：按本文档已确认的3个提交方案实施。
3. 全库查重＋基础质量检查：作为知识入库前置判断的第一期，可提前建设。

需要在知识效果追踪和人工复盘完成后启动：

4. 入库价值判断：作为第二期，结合真实使用效果判断一段内容是否值得被知识库学习。

上述编号表示路线图中的4项能力，不表示必须按照数字串行执行。第1、2、3项可以并行；第4项必须等第1、2项建立可用的反馈数据后再启动。

## 二、人工复盘：已冻结的产品规则

1. 用户自主决定何时复盘，不强制发布后立即触发。
2. 人工复盘标签可以多选：
   - 选题角度新颖
   - 引用具体案例或经典原文
   - 标题结构有效
   - 表达风格贴合IP
   - 蹭中热点或时事
   - 发布时间平台选得好
   - 其他
3. 文字说明必填，用户必须写清楚具体理由。
4. 待复盘清单只收录FlowPilot内部、可追溯的已发布内容。
5. 外部内容可以复盘存档，但不进入学习闭环。
6. 一条内容默认只有一份有效复盘；修改时更新原记录并保留更新时间。
7. 待复盘内容可以标记为“暂不复盘”，但不能显示为已完成，也不能参与学习。

## 三、人工复盘：当前状态诊断

当前代码不能只增加几个标签，还需要先补齐“已发布→待复盘→暂不复盘／已完成”的生命周期。

1. 脚本目前只有“草稿／定稿／已拍摄”，没有“已发布”状态。
2. 复盘记录支持`analysis: null`，工作台也尝试统计待复盘记录，但现有页面不会主动创建这种记录，所以入口基本不起作用。
3. 当前只有点击“开始六层复盘分析”并成功保存后才产生复盘记录，无法先登记发布、过几天再回来处理。
4. 同一脚本可以重复创建多条复盘，存储层没有“一条内容一份有效复盘”的约束。
5. 复盘只有创建时间，没有修改时间，也没有人工标签、必填说明和“暂不复盘”状态。
6. 外部内容不可追溯、不能参与学习的隔离已经存在，可以直接复用。

## 四、人工复盘：建议的数据流程

复用现有`VideoReview`记录，不再建立第二套独立存储：

```text
登记内部内容已发布
→ 待复盘
├─ 暂不复盘：保留记录，不参与学习
└─ 完成复盘：多选标签＋必填说明
   → 更新同一条记录
   → 保留创建时间和最新修改时间
```

外部内容仍可直接复盘和修改，但不进入待复盘清单，也不参与学习。

历史旧复盘保留原样，标记为“待补人工复盘”；补齐必填说明前，不把它显示成已经完成的新式人工复盘，也不删除原记录。

## 五、知识效果追踪：断点与修复方向（已确认）

当前断点已经确认：知识使用记录、脚本和发布复盘之间缺少可追溯的关联字段。

1. 知识使用记录目前没有保存对应的选题ID、脚本ID和复盘ID。
2. 脚本没有保存本次实际使用的知识条目编号。
3. 发布复盘虽然能追溯到选题和脚本，但无法继续追溯到当时使用的知识。
4. 脚本工厂目前在检索完成时就记录“已用于脚本”，这个时机过早：它既不能证明AI真正采用了该知识，也不能证明脚本最终生成并保存成功。

修复方向：

1. 为知识使用记录补齐选题ID、脚本ID和复盘ID，使每次使用都能追溯到具体内容资产。
2. 脚本保存本次实际采用的知识条目，不把“检索到”直接等同于“已使用”。
3. 将“已用于脚本”的记录时机后移：至少要等脚本生成成功，并能确认相应知识确实进入最终结果或生成依据。
4. 发布复盘通过脚本ID和选题ID回溯知识条目，再结合人工复盘理由和真实表现数据，形成可信的知识效果记录。

后续设计“暂定经验”字段结构时，必须把以下两条链路作为同一套学习闭环共同设计，不能拆成互不关联的系统：

```text
选题 → 脚本 → 发布复盘 → 真实表现
知识条目 → 脚本 → 发布复盘 → 真实表现
```

在效果追踪机制建立之前，不建议继续大量补充知识库内容。当前优先回答“哪些知识真正帮助了内容表现”，再决定补充哪些知识。

## 六、知识入库前置判断

### 第一期：全库查重＋基础质量检查

输入范围：

- 当前只支持文字和逐字稿。
- 暂不支持直接提交视频文件进行判断。

产品能力：

1. 对待入库内容进行跨全库检索，不只检查本次导入批次内的重复。
2. 输出已有相似内容、来源和相似原因，让人工能看懂“像在哪里”。
3. 同时做基础质量检查，但只判断内容表面是否完整、清晰、具有可用信息，不冒充真实效果判断。具体检查项在实施前另行冻结。

产品边界：

1. 系统只提供查重结果、质量提示和判断依据。
2. 第一期不自动合并、不自动删除，也不因相似度较高就自动覆盖原有内容。
3. 最终是合并还是保留，由人工确认。
4. 表达相似不等于知识价值相同；系统必须保留相似原因和来源，不能只给一个没有解释的分数。

### 第二期：结合真实效果的入库价值判断

第二期回答的是：“这段内容是否真的值得被知识库学习？”

启动条件：

1. 知识效果追踪已打通，能将知识条目与脚本、发布复盘和真实表现关联起来。
2. 人工复盘功能已建立，能保留人工选择的原因标签和必填说明。
3. 前两项已累积足够的可用反馈数据，能支撑判断，而不是只有空的字段和关联。

定位与边界：

1. 判断必须同时参考内容本身、历史使用情况、人工复盘理由和真实表现。
2. 在依赖建立前，AI只能判断表面内容质量，不能将结果包装成“值不值得学习”的真实效果结论。
3. 这是第二期能力，不与第一期查重功能捆绑上线。

## 八、人工复盘本次明确不纳入的内容

1. 不生成“暂定经验”。
2. 不写入复盘经验库。
3. 不设计经验字段、置信度和引用方式。
4. 不修改选题董事会引用和解释经验的逻辑。
5. 原则上不修改AI复盘接口。

## 九、依赖关系与执行说明

```text
知识效果追踪 ─┐
                  ├─→ 入库价值判断（第二期）
人工复盘功能   ─┘

全库查重＋基础质量检查（第一期）
─→ 可独立、并行推进
```

1. 知识效果追踪、人工复盘、全库查重＋基础质量检查三项互不依赖，可以并行开发和验证。
2. 全库查重虽然在整体产品排期中排在知识效果追踪和人工复盘之后，但它没有技术依赖，可以适当提前。
3. 入库价值判断同时依赖知识效果追踪和人工复盘，不能只完成其中一项就启动。
4. 第二期的启动标准不是“功能页面已上线”，而是已经形成可用的真实反馈样本。
